# Animated Animation/Bild templates: implement for large (Pi) screens now, defer small (ESP32) screens

Animation/Bild's fixed template library (`domain/content.ts`'s `TEMPLATES`) now includes two templates that carry their own CSS `@keyframes` animation (a rotating arrow, a wobbling raute) alongside the plain static ones. Previously, applying any template — animated or not — rasterised a single frozen frame; the CSS animation only ever played in the small menu picker icon (a literal `<img>` in the DOM), never in the applied preview or on a panel. We implemented real animation end to end for large screens: the frontend samples the template's own keyframes into a frame strip (`render/animatedTemplate.ts`) and ships it as a new `frames` field alongside the existing `pal4` bitmap (`docs/wire-format.md`), and `pi_display.py`/`compositor.py` step through it by elapsed time — the same mechanism Lauftext's `scroll` already uses, generalised from a continuous pixel offset to a stepped frame index. Small-screen (ESP32) support is deferred to a written plan (`docs/plan-esp32-animation-frames.md`).

## Why staged rather than both at once

Same reasoning as [ADR 0001](./0001-phase-lauftext-background-by-hardware-kind.md): the Pi path is backend/frontend-only and fully verifiable with the existing test suites and a browser preview. The ESP32 path needs a binary-envelope version bump and firmware changes whose correctness can only really be confirmed by flashing and visually checking the physical wall — outside what this session can do. Shipping the verifiable half now, with a concrete written plan for the rest, avoids putting unverified behaviour on hardware that's actively part of the wall.

## Consequences

- Until the ESP32 firmware ships, a small-screen selection can still have an animated template applied to it, but shows it as a static frame — specifically frame 0, the first slot of the frame strip — rather than animating or corrupting. This degrade is automatic (`compose.py`'s `_is_sliceable` treats `frames` like `scroll`: ship the whole strip unsliced) and needs no small-screen-specific UI warning, unlike ADR 0001's Lauftext-background case: there the old small-screen behaviour was "always renders on black" (a visible loss worth calling out), where here it's "shows the same static icon a non-animated template always has" (not a loss relative to what small screens already do today, just a feature that hasn't reached them yet).
- The binary MQTT envelope will need a version bump when this phase lands — see `docs/plan-esp32-animation-frames.md` for the proposed header layout. If ADR 0001's phase 2 (background) lands in the same work session as this one, prefer combining both into a single version bump with two new flag bits rather than stacking two separate bumps; the two plan documents were written to compose that way but haven't been reconciled against each other since neither has actually been implemented yet.
- `docs/wire-format.md`'s JSON envelope already documents `frames` as implemented (it runs today, for large screens); the binary envelope section documents it as explicitly not yet encoded there.
- The sample rate started as a per-edit control (an fps slider in `AnimationPanel`, 2–30) specifically so it could be tested directly on the physical large screens rather than guessed at from payload-size math alone. After testing, 16fps was chosen as the rate that looks right on the panels; the control was then removed and the rate fixed as `domain/content.ts`'s `ANIMATION_FPS` constant, since it was never meant to be an end-user-facing setting — every animated template now converts at this one rate, with no per-edit choice.
